## 🛡️ La philosophie : "Never Trust, Always Verify"

Le segment `SEG-SRV` ne doit pas être un réseau "ouvert". Pour garantir l'intégrité du pare-feu, j'ai défini trois objectifs de filtrage :

1. **Isoler l'interface de gestion (GUI)** : Seul mon poste identifié peut configurer le cluster.
2. **Brider les flux de services** : Le poste pilote ne peut interroger que les services nécessaires (DNS de l'AD).
3. **Bloquer par défaut** : Tout ce qui n'est pas explicitement autorisé est rejeté.

## 🖥️ Étape 0 — Prérequis VMware : assignation du LAN Segment

Avant toute configuration réseau, la machine qui jouera le rôle de poste pilote doit être connectée au bon segment virtuel. Dans VMware Workstation, chaque VM doit avoir sa carte réseau assignée au **LAN Segment SEG-SRV** — et non en NAT ou Host-Only, qui introduiraient du trafic parasite.

## 🏷️ Étape 2 — Création des alias (abstraction logicielle)

Plutôt que d'utiliser des adresses IP brutes dans les règles, les **alias** permettent une gestion plus lisible et évitent les erreurs de saisie. Si l'IP du poste pilote change un jour, une seule modification dans l'alias suffit — toutes les règles qui y font référence sont mises à jour automatiquement.

- **AdminHosts** : contient l'IP statique du poste de gestion (`10.0.1.50`)
- **Poste_Pilote_GUI net** : représente l'ensemble du sous-réseau SEG-SRV

## 🔒 Étape 7 — Isolation DNS : mise en place du Split-Horizon
 
### Pourquoi c'est important ?
 
Par défaut, un contrôleur de domaine Windows avec la récursion DNS activée peut résoudre **n'importe quel nom externe** — ce qui crée une surface d'exfiltration potentielle via DNS. Dans une architecture segmentée conforme à l'ANSSI, le Management Plane ne doit pas pouvoir joindre Internet, y compris via des requêtes DNS.
 
L'objectif est d'obtenir ce comportement strict :
 
```
Poste pilote → AD01 (DNS)
AD01         → autorité sur infra.formation.local uniquement
AD01         → refuse toute résolution externe (récursion désactivée)
Résolution externe → impossible depuis le segment
```
 
### Désactivation de la récursion DNS sur AD01
 
La récursion permet à un serveur DNS de résoudre des noms pour lesquels il n'est pas autoritaire — en interrogeant d'autres serveurs DNS sur Internet. On la désactive pour que l'AD01 ne réponde qu'aux zones qu'il gère.
 

<ProjectImage
  src="/images/projets/firewalling-edge/opnsense/seg-srv/12.5.png"
  alt="Récursion DNS désactivée sur AD01 — Enable: False"
  caption="Get-DnsServerRecursion confirme Enable: False — l'AD01 ne résout plus que ses propres zones"
  maxWidth="600px"
/>
 
### Configuration d'Unbound — Domain Override vers AD01
 
Sur OPNsense, Unbound est configuré avec un **domain override** : toutes les requêtes pour `infra.formation.local` sont déléguées à l'AD01 (`10.0.2.10`). Pour le reste, Unbound résout de manière récursive — mais uniquement depuis OPNsense, pas depuis les segments internes.
 
Cette configuration implémente le **DNS split-horizon** :
- Les noms internes → AD01 fait autorité
- Les noms externes → Unbound résout, mais les segments internes ne peuvent pas l'atteindre directement.

  src="/images/projets/firewalling-edge/opnsense/seg-srv/13.png"
  alt="Configuration Unbound — domain override infra.formation.local vers 10.0.2.10"
  caption="Domain override Unbound : toutes les requêtes .infra.formation.local sont transmises à l'AD01"
  maxWidth="700px"

## 🛡️ Étape 8 — PKI Locale : Authentification de la WebGUI

Pour parfaire la sécurité du poste pilote, j'ai remplacé le certificat auto-signé par défaut par une **chaîne de confiance personnalisée**. L'objectif est d'éliminer les alertes de sécurité et de garantir l'identité du cluster sans dépendre de l'Active Directory.

### 1. Création de l'Autorité de Certification (CA) interne

La première étape consiste à transformer l'OPNsense en autorité émettrice. J'ai configuré une CA nommée `CA-INFRA-TOULON` avec un chiffrement RSA-2048 et une durée de vie de 10 ans.

<ProjectImage
  src="/images/projets/firewalling-edge/opnsense/seg-srv/15.png"
  alt="Configuration de l'autorité de certification CA-INFRA-TOULON"
  caption="Création de la CA racine locale — le point de départ de notre chaîne de confiance"
  maxWidth="600px"
/>

### 2. Génération du certificat serveur signé

J'ai ensuite généré un certificat pour la WebGUI (`CERT-GUI-OPNSENSE`) signé par notre nouvelle CA. Ce certificat inclut les **Subject Alternative Names (SAN)** pour la VIP (.254) ainsi que les IP réelles des nœuds (.252 et .253), évitant toute alerte de nom de domaine invalide.

<ProjectImage
